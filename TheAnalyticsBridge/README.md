# Analytics Bridge: Ingestion and Processing

Run these commands from `TheAnalyticsBridge` with Python 3.12 and Pipenv installed:

```powershell
pipenv sync
pipenv run python main.py
```

Configure the settings below in `.env` before the first run; do not overwrite an existing configuration.

Start the Legacy Core with its HTTP launch profile and the PowerShell simulator separately. The bridge starts both readers in one process and passes the same `EventQueue.put` callback to each. Valid new legacy records and complete attack log lines are enqueued as typed log objects. A third task scores each log and saves it in the recent event store. A diagnostic task checks the store once per second and prints its full snapshot as JSON when changed. Stop with Ctrl+C; all background tasks are cancelled and the HTTP client and watchdog observer are closed.

The processor consumes queued logs, scores them through the selected LangChain model (Google Gemini or local Ollama), and retains processed events in memory. Startup may print an empty snapshot before processing begins; subsequent changed snapshots include the retained original logs and scores. No API/SSE endpoint is implemented yet. When the queue is full, producers wait without advancing past an unaccepted record. Stopping the bridge discards queued events and stored history; starting again replays available source data. There is no cross-process shared queue or store.

Set the queue and recent event store capacities in the selected environment file (already added locally). Both must be positive integers:

```dotenv
EVENT_QUEUE_CAPACITY=1000
EVENT_STORE_CAPACITY=1000
```

The standalone `python -m ingestion.legacy_api_poller` and `python -m ingestion.attack_log_watcher` commands still print events for diagnostics. They do not use the shared queue; use `main.py` for combined ingestion.

## Package Layout

- `configuration`: the shared `ENV_FILES` mapping and `load_environment()` function. Loading is explicit at startup, not on import; the function returns the bridge directory for resolving relative paths.
- `models`: immutable source and processed records. `ILog` requires `from_json()` and `to_payload()`; serialization returns JSON-compatible fields without requiring dataclasses. Source models emit ISO-formatted timestamps, preserve offsets, and keep attack times date-free.
- `ingestion`: the source readers, which use the shared models and environment loader.
- `messaging`: the bounded `EventQueue`, which depends on `ILog` rather than the source readers.
- `processing`: `EventProcessor` and narrow interfaces in `contracts.py`: `EventSource`, `EventScorer`, `EventWriter`, and `EventReader`.
- `integrations`: `LlmScorer`, implementing `EventScorer` with a LangChain prompt, chat model, and typed danger-score output parser.
- `integrations/model_strategies.py`: `ModelStrategy` protocol with Gemini and local implementations. `create_chat_model()` selects a strategy from `LLM_MODEL_TYPE`; the processor and scorer remain provider-independent.
- `storage`: bounded in-memory `EventStore` for processed history, independent of processing and HTTP.

```python
from configuration import load_environment
from models import AttackLog, ILog, LegacyLog
from messaging.event_queue import EventQueue
```

## Configuration

The readers live in the `ingestion` package. Run their module commands from `TheAnalyticsBridge`. Startup uses `python-dotenv` to load the environment-specific file from `TheAnalyticsBridge`, not from the `ingestion` folder. Set `APP_ENV` in the shell or deployment configuration before launching Python:

- `development` (default) or `dev`: load `.env`.
- `production` or `prod`: load `.env-prod` only, without falling back to `.env`.
- Other values fail at startup to catch configuration mistakes.

Existing environment variables take precedence over the selected file. Combined ingestion requires all four poller settings below, both watcher settings, `EVENT_QUEUE_CAPACITY`, `EVENT_STORE_CAPACITY`, and the LLM settings below. A missing file is allowed when all required settings are supplied by the deployment environment. Both local environment files are ignored by Git. The local legacy API needs no secret; Gemini requires `GOOGLE_API_KEY`.

`LLM_MODEL_TYPE` is required and accepts `gemini` or `local` (ignoring case and surrounding whitespace). Unknown values fail at startup. Local development is currently set to:

```dotenv
LLM_MODEL_TYPE=local
LLM_MODEL=llama3
```

The local strategy reads `LLM_MODEL` and creates `ChatOllama` with temperature zero and the object JSON schema generated by `DangerScoreResponse.model_json_schema()`. The response contains a named integer field, for example `{"danger_score": 90}`, rather than a bare number. The same Pydantic model validates responses in the scorer, enforcing the 1-100 range. A valid number does not guarantee an accurate danger assessment. Local mode does not require `GOOGLE_API_KEY`. Install Ollama, keep its local server running (normally `http://localhost:11434`), and download the configured model once, for example with `ollama pull llama3`. If the server is not already running, start it with `ollama serve`. The Ollama SDK honors `OLLAMA_HOST` if set; leave it unset to use the default local endpoint.

To switch back to Gemini, set `GOOGLE_API_KEY` privately in the selected environment file or deployment environment. Never commit the key. Configure:

```dotenv
LLM_MODEL_TYPE=gemini
LLM_MODEL=gemini-2.5-flash
```

Restart the bridge after changing providers. For Gemini, the model must be available to your Google API key; change `LLM_MODEL` to another supported Gemini chat model when needed. Startup sends no scoring request until an event is consumed. In Gemini mode every processed log, including replayed history, is sent to Google with its original fields (including IP addresses) and may incur usage costs. Local mode sends logs to the configured Ollama server instead, with no automatic cloud fallback. Only use logs approved for the selected service. Requests are sequential; a slow model can fill the bounded ingestion queue. No live provider request is made by the test suite.

For production using Pipenv, disable its automatic `.env` loading so development values are not injected before Python selects `.env-prod`:

```powershell
$env:APP_ENV = "production"
$env:PIPENV_DONT_LOAD_ENV = "1"
pipenv run python main.py
```

Provision `.env-prod` with all the settings described here, or inject them through deployment configuration. Do not put `APP_ENV` only inside `.env-prod`: it must be known before choosing the file. `override=False` intentionally preserves deployment-provided values; it does not control which file is selected.

## Design

- `LegacyLog` validates the API's camelCase JSON fields and provides an immutable typed record.
- `LegacyApiPoller` fetches and deduplicates records. It accepts an externally owned `httpx.AsyncClient` and an async handler, so HTTP transport and downstream processing can be substituted without inheritance.
- `poll_once()` performs one poll and returns the number of accepted records; failures propagate to the caller. `run()` polls immediately, catches failures, and waits the configured interval after each attempt before retrying. Cancellation propagates for application shutdown.
- A record is remembered only after the handler completes successfully. Invalid individual records are skipped with a warning. HTTP, JSON, and handler failures are retried on the next polling cycle without logging response bodies or exception messages.
- Deduplication uses all four fields and a bounded, in-memory least-recently-used cache. Identical records cannot be distinguished without upstream event IDs. Restarting Python or evicting old entries permits replay; this is not durable exactly-once delivery. Keep the capacity larger than the API snapshot size.
- Use one `run()` task per poller instance; do not call `poll_once()` concurrently with it. The caller owns client cleanup and task cancellation.

The bridge entry point passes one bounded `EventQueue`'s `put` method to both readers. Scoring and event history are separate from ingestion; SSE is not implemented yet. A handler that performs a side effect and then raises can be called again; consumers should account for possible replay.

## Event Processing and Storage

```text
LegacyApiPoller --+
				 +--> EventQueue --> EventProcessor --> EventStore
AttackLogWatcher-+                       |
									LlmScorer
```

- `EventProcessor` depends on consumer-owned Python protocols: `EventSource` (`get`, `task_done`), `EventScorer` (`name`, async `score`), and `EventWriter` (`append`). It does not import the concrete queue, scorer, or store. Startup chooses and injects them.
- The console printer depends only on `EventReader.snapshot()`, not the concrete store. `EventQueue` and `EventStore` satisfy protocols structurally through matching methods; explicit inheritance is unnecessary. Read and write contracts are separate so each consumer requests only what it uses. Readers retain their injected async callbacks; no unused broadcaster interface is introduced.
- The scorer serializes logs through `ILog.to_payload()`. `ProcessedEvent.to_payload()` uses that same contract for nested log output, removing dataclass assumptions from downstream serialization. Console timestamps now use ISO format (`T` between date and time). Non-dataclass log implementations work in both scoring and console output, provided they implement the log contract. These payloads preserve source field names; they do not perform full cross-source schema normalization.
- Each `ProcessedEvent` is frozen and contains a unique UUID, original typed log, integer `danger_score` from 1 to 100, `scoring_method`, and UTC `processed_at`. Source timestamps remain unchanged: attack logs only contain a time of day, not an invented date.
- `LlmScorer` uses `ChatPromptTemplate | model | PydanticOutputParser(pydantic_object=DangerScoreResponse)` with async invocation. The short prompt requests a JSON object containing `danger_score` and treats log contents as untrusted data. Logs are serialized through their payload contract. The Pydantic response requires an integer from 1 to 100, rejects string/float/bool coercion, and forbids extra fields. Invalid responses raise `OutputParserException`; LangChain also supports JSON wrapped in Markdown fences. The chain returns a validated response object, and the scorer extracts `.danger_score` so the processor still receives an integer. There is no custom regex or numeric output parser. Stored results remain labelled `llm`; these are model estimates, not calibrated probabilities or proof of compromise.
- LLM requests have no application deadline: the scorer awaits the chain directly, Gemini uses `timeout=None`, and Ollama retains its default disabled client timeout. `LLM_REQUEST_TIMEOUT_SECONDS` is no longer read, even if present in an environment file. A stalled request can block processing indefinitely and eventually fill the queue; Ctrl+C still cancels it. Services can still terminate requests or return errors. SDK retry defaults are unchanged. Provider errors and malformed output propagate with no fallback, retaining the processor's fail-fast policy. Both providers use temperature zero. The legacy API request timeout remains separate and unchanged.
- `EventStore.append()` retains the latest `EVENT_STORE_CAPACITY` events, evicting the oldest when full. `snapshot()` returns a detached immutable tuple, oldest first, for future history consumers. Store operations are synchronous and intended for this single event loop, not concurrent threads or multiple server workers.
- Processing takes one log, scores it, stores the result, and balances queue accounting using `task_done()` in `finally`. `join()` means work attempts have finished, not that all events were saved successfully. Scoring, validation, or storage errors propagate and stop the task group rather than silently dropping failures and continuing. There are no automatic processor retries or dead-letter storage yet.
- Cancellation can discard an in-flight event, and shutdown does not drain the queue. Restart replays available input but changes processed IDs and loses previous history. This is bounded, volatile demo storage, not durable or exactly-once delivery.
- API snapshots, SSE broadcasting/replay, global gauge aggregation, and AI batch summaries remain future work. LLM scoring currently assesses individual logs, not batches or recent history. LangChain core, its Google Gemini adapter, and its Ollama adapter are installed and locked in Pipenv.

## Attack Log Watcher

Install the locked dependencies using `pipenv sync`. From `TheAnalyticsBridge`, run:

```powershell
pipenv run python -m ingestion.attack_log_watcher
```

Start `TheChaosMonkey/AttackSim.ps1` in another terminal. The watcher prints accepted events as JSON; Ctrl+C stops it and joins its watchdog observer thread. It can start before the log file exists, but the containing directory must already exist. The legacy API is not needed to run the watcher.

Add these settings to the selected environment file (already added to the local development configuration):

```dotenv
ATTACK_LOG_PATH=../TheChaosMonkey/live_stream.log
ATTACK_WATCH_RETRY_SECONDS=2
```

Relative paths are resolved from the bridge directory, not the terminal's working directory. The watcher uses the same `APP_ENV` selection and deployment-variable precedence described above; disable Pipenv's dotenv preloading for production. The retry interval is a reconciliation interval, not a delay before processing filesystem notifications.

- `AttackLog` validates the simulator schema: a time of day, a nonempty attack type, severity 1-9 (matching PowerShell's exclusive upper bound), and a valid origin IP. It preserves the source time without inventing a date or timezone.
- `AttackLogWatcher` owns the file cursor and observer lifecycle. An injected async handler controls where events go; pass a bounded queue's `put` method to connect later processing without coupling the watcher to scoring or SSE.
- A small watchdog handler filters target-file notifications and uses `loop.call_soon_threadsafe` to wake the async reader. File reads run through `asyncio.to_thread`; observer callbacks never perform parsing or delivery.
- `read_once()` reads up to 100 complete UTF-8 JSON lines and returns the accepted count. `run()` drains remaining batches, then waits for notifications or periodic reconciliation. Startup reads existing lines from the beginning. Identical attacks on separate lines remain separate events.
- The byte cursor advances after successful delivery, or after explicitly skipping a malformed completed line. Incomplete lines wait for a newline, including split UTF-8 characters. Handler failures retry without skipping the failed line, even when no further writes arrive.
- The log is assumed to be append-only. The watcher tracks only a byte offset and waits if the file has not been created yet. Deletion, replacement, rewriting, and truncation while running are unsupported; stop the watcher before resetting the file, then restart it.
- Cursor state is in memory and restarting replays the file. This is not durable exactly-once delivery; a handler that commits a side effect then raises can cause replay. The reader is intended for the simulator's small JSON lines, not arbitrarily large untrusted lines.
- `read_once()` calls are serialized. Run only one observer task per watcher and one bridge process for this in-memory design. Failures log error types rather than raw log contents.

## Tests

```powershell
pipenv run python -m unittest discover -s tests -v
```

Poller tests use HTTPX's mock transport without requiring the .NET API or an external network. Watcher tests use temporary files and include a real watchdog observer integration check, initial creation, appends, partial writes, retry, configuration, and cancellation cleanup.

Bridge tests run both real reader implementations, the processor, and the LangChain scorer against mocked HTTP, fake chat responses, and temporary files. They check scored history, provider configuration, API outage isolation, and cancellation under queue backpressure. Processing tests cover replaceable dependencies, immutable bounded snapshots, unique event IDs, score validation, failures, and cancellation accounting. Scorer tests cover both source schemas, strict 1-100 parsing, prompt data handling, pending requests without a scorer deadline, cancellation, and provider errors without using a real API key.
